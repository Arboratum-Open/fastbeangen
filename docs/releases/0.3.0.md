# FastBeanGen 0.3.0 — prepared, not published

This is the local release candidate description, not a release announcement. No tag, GitHub draft/release or Maven Central upload is created by the preparation commands. Do not remove the local Maven repository from consumer configuration until 0.3.0 is actually available remotely.

## Highlights

- Java **21 minimum**, Java 21 bytecode, with the build/test/consumer matrix targeting actual Java **21 and 25**.
- Official Gradle **9.9.1** wrapper and pinned stable dependencies; no JCenter/Bintray dependency or publication assumption. Core, document generation and executable examples remain separate modules.
- Modern Reactor acknowledgement/backpressure and blocking-capable scheduler integration, Jakarta persistence/Hibernate/OpenCSV adaptations, and bounded embedded-database examples.
- First-party distribution under **LGPL-3.0-only**, including both `LICENSE` (LGPL v3) and `COPYING` (its incorporated GPL v3 terms) in first-party binary, sources, Javadoc and example JARs.
- Restored published-0.2.17 database contracts, strict local publication checks and an independently compiled POM-only consumer.
- Java/JUnit verification driven by Gradle, including publication/license/release guards and bounded example checks; no Python runtime dependency.
- The CUD example now uses its existing 20 operations/second limiter with the existing five-second warm-up before processing each operation. Per-wall-clock counts and batch sizes intentionally change, not the library's seeded values or global feed pacing. The 180-second example deadline, six checkpoints, one-minute query and 20,000/20/47 CSV assertions remain unchanged; identical asynchronous interleavings are not promised.

The Maven coordinates remain `com.arboratum:fastbeangen:0.3.0` and `com.arboratum:fastbeangen-doc:0.3.0`. Examples are not a third Maven publication.

## Migrating from published 0.2.17

The historical Git modernization baseline was not identical to the last published 0.2.17 artifacts. The release preparation therefore compares the actual published binaries, sources and POMs; their hashes and execution boundary are recorded in [the published reference](../../verification/published-compatibility/README.md).

The restored API includes:

- `filteredView(predicate, maxTryPerSelect)` and `transformedView(function, type, maxTryPerSelect)`, including applicable composed/union views. Existing convenience overloads remain and use the published default `Integer.MAX_VALUE` budget. Empty input and exhausted/non-positive budgets return `null`.
- `Entry.wasInInitialDataSet()` and `DataSet.EntryRef.wasInInitialDataSet()`; provenance is retained by transformed entries/references. Initial indices include deleted slots, not only the requested live count. Later creations are not initial entries.
- Custom `DataView`/`Entry` implementations from the pre-release Git baseline must implement the bounded overloads/provenance method, not just the convenience overloads. Implementations already conforming to published 0.2.17 retain those contracts.
- `withDeletionCheck(Predicate<Entry<T>>)` receives the operation entry, as published. Callers of the incompatible unpublished value-predicate Git variant must adapt the predicate, using `entry.lastVersion().block()` when the value is needed. The two generic signatures cannot coexist under Java erasure.
- `UpdateGenerator.canApplyOn(value, ref)` receives the matching reference. The pre-release one-argument override remains supported through the default bridge. Updates still mutate values in place; immutable-update semantics are not introduced.

Three cases fail against the original published binary and pass against the corrected candidate: composed-view budget propagation, successful transformed selection (old null-lock failures), and initial provenance after a deleted slot. These are explicit defect corrections, not claims that all reference tests passed. The same eight fixed assertions give **five passes and three failures** against 0.2.17. A preparation-time public-descriptor comparison covered 358 descriptors across 59 public classes with no missing candidate descriptor, accounting for inherited `DataView` methods. Neither that finite comparison nor the representative runtime tests prove compatibility for every dependency, seed, configuration or concurrency schedule.

Java 8 consumers must upgrade to Java 21. Framework/API dependency changes are described in [the migration guide](../modernization.md). Existing deterministic fixtures, PRNG, dictionaries/templates, assertions and statistical/document-size tolerances remain protected. No changed generated values have been accepted in previously working seeded scenarios. The historical internal dataset/Monte Carlo constructor repair is separately documented in that guide.

## Licensing and limits

LGPL is weak copyleft, not a permissive MIT/Apache license. Distribution must meet applicable notices, corresponding-source/modification and replacement/relinking conditions; consult both full license texts and the [distribution guidance](../../README.md#license). Dependencies and the wrapper retain their own licenses/notices. Earlier releases and GPL rights already granted are not rewritten. Owner rights attestations are not an independent legal/provenance audit.

No comprehensive security audit, performance guarantee, warning-free build or exhaustive generated-byte identity is claimed. Existing compilation/Javadoc/logging warnings and the test-only PalDB maintenance limitation remain visible. Final acceptance depends on the candidate's actual independent verification records, not an earlier master's CI or the presence of a configured matrix.

## Prepare and inspect local assets

From the repository root, with the supported JDKs available:

```sh
./gradlew --no-daemon --console=plain --max-workers=1 -PjavaVersion=21 check assemble publishAllPublicationsToLocalRepository verifyPublication
./gradlew --no-daemon --console=plain --max-workers=1 -PjavaVersion=21 verifyReference verifySigningGuards
./gradlew --project-dir verification/consumer --no-daemon --console=plain --max-workers=1 -PjavaVersion=21 run
./gradlew --no-daemon --console=plain --max-workers=1 -PjavaVersion=21 stageRelease verifyRelease
```

Run the applicable build/consumer checks on Java 25 as well; `--release 21` remains fixed. Final Runtime checks cover both supported JDKs without unnecessarily repeating the entire heavy suite during Builder development. The example verifier is `./gradlew -PjavaVersion=21 verifyExamples` (or `25`); it runs Java/JUnit checks over bounded workloads including a one-minute query. `check` includes `verificationTest`; the [verification case mapping](../../verification/README.md) records all former 24 guard methods/subcases and the added Java regressions. `verifyReference` uses Java 21 to retain the original published-runtime characterization and verifies fresh XML with exactly the three known failures; that successful characterization does not turn the original failing build green. Large historical tests need a 4 GiB test heap and approximately 2 GiB of temporary disk data; use one worker.

Ordinary preparation needs no credentials. On Unix, prefix Gradle commands with `env -u SIGNING_KEY -u SIGNING_PASSWORD` to explicitly keep an already configured signing environment out of unsigned preparation. Never print keys/passwords or add them to files/history.

`build/release/0.3.0/` contains six library JARs (binary/sources/Javadoc), two POMs, `RELEASE-NOTES.md`, `release-manifest.json` and `SHA256SUMS`. The manifest identifies the base commit, modified-worktree status and a fingerprint of product source/docs/build inputs, including explicit tracked-deletion markers and excluding generated output, Native formals and local bootstrap. A dirty candidate is not an exact release commit. SHA-256 values cover the actual payloads and the checksum list also covers the manifest. `verifyRelease` checks them against the current local publication, notes and source identity. Staging refuses foreign, linked or manually changed output rather than overwriting it; only a previously intact generated set can be restaged.

## Later publication checklist — separate authorization required

1. Accept the independently verified result, finish the change under the chosen Git/Archive process, and obtain explicit commit/push/PR/merge authorization as needed. Recheck CI for the final commit, then rebuild and verify the assets from that identity. Recheck tag/version collisions before any publication; preparation-time availability is not a reservation.
2. Obtain explicit authorization for the `v0.3.0` tag and GitHub release. Bind them to the verified final commit, review these notes and the exact asset manifest, and do not silently substitute the preparation base commit. No draft or release is created now.
3. For Central, qualify publishing rights for `com.arboratum`, securely provide an authorized ASCII-armored private key through `SIGNING_KEY` (and optional `SIGNING_PASSWORD`), and verify its ownership/fingerprint and public-key availability. Do not generate or import a key as an implicit workaround.
4. Under that separate authorization, run `./gradlew --no-daemon --console=plain --max-workers=1 bundleCentral`, then `./gradlew verifyCentralBundle`. The bundle is `build/distributions/fastbeangen-central.zip`. The tasks allow only the two intended version directories, require valid Maven metadata/legal texts, check required MD5/SHA-1 and existing SHA-256 checksums, and require signature files for every publication artifact. Missing/blank/unusable signing input must fail; an old ZIP left after failure is not a successful fresh bundle.
5. The Java Central checks driven by Gradle are **structural/content checks, not cryptographic signature verification**. Verify every detached signature against the intended public-key fingerprint (for example with GnuPG) before upload. Synthetic signatures used in unit fixtures are never a releasable bundle.
6. Obtain explicit upload/publication authorization, use the [Central Portal upload process](https://central.sonatype.org/publish/publish-portal-upload/), inspect its validation outcome, and publish only under the intended final identity. A valid local ZIP is not Portal acceptance. Verify remote artifacts/coordinates after publication before updating the unreleased status or advertising remote dependencies.

Real-key signing/cryptographic verification, public-key availability, namespace/access authorization, Central validation/acceptance, and remote release/tag creation remain **unverified/not performed by unsigned preparation**. Consult the current [Central requirements](https://central.sonatype.org/publish/requirements/): SHA-256 release hashes do not replace its required MD5/SHA-1 checksums.
